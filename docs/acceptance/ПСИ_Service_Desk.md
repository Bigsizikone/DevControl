# Программа сценариев и приемки Service Desk

Статус: проект протокола приемочных испытаний  
Версия: 1.0  
Дата: 08.09.2026

## 1. Назначение

ПСИ определяет сквозные пользовательские сценарии, по которым заказчик принимает Service Desk как единый сервис. Детальные проверки выполняются по [ПМИ](./ПМИ_Service_Desk.md), требования — по [ЧТЗ](./ЧТЗ_Service_Desk.md).

## 2. Участники приемки

| Участник | Зона проверки |
| --- | --- |
| Представитель заказчика | подтверждение результата и бизнес-процессов |
| Владелец Service Desk | обращения, маршрутизация, SLA, отчетность |
| Администратор | НСИ, роли, права, настройки |
| Представитель ИТ | интеграции, развертывание, мониторинг |
| Представитель ИБ | доступ, аудит, файлы и события безопасности |
| Ключевые пользователи | удобство форм, карточек и рабочих сценариев |

## 3. Сквозные сценарии

### S-01. Создание и исполнение обращения

Предусловия: в НСИ есть активный пользователь, тип и вид заявки, группа поддержки и правило маршрутизации.

1. Инициатор открывает «Новое обращение».
2. Выбирает пользователя, вид «Запрос на обслуживание», вводит тему и описание.
3. Система автоматически формирует номер и код, переносит основные данные пользователя.
4. Диспетчер запускает маршрутизацию.
5. Система назначает группу, исполнителя, приоритет и SLA.
6. Исполнитель открывает отдельную карточку, добавляет комментарий и переводит обращение в работу.
7. Исполнитель устанавливает «Требуется выезд», выбирает дату и время.
8. После выполнения исполнитель указывает результат, а инициатор видит обновленный статус.

Ожидаемый результат: обращение прошло полный жизненный цикл, все изменения и комментарии сохранены, аудит сформирован.

### S-02. Закупка по обращению

1. В карточке обращения установить «Требуется закупка».
2. Проверить наличие первой строки номера ERP.
3. Ввести номер до 20 символов и добавить еще одну строку.
4. Сохранить параметры.

Ожидаемый результат: все номера сохранены, для каждого нового номера создан комментарий «Создана заявка на приобретение №…», лишние символы отклонены.

### S-03. Ремонт оборудования

1. Создать обращение с видом «Ремонт».
2. Выбрать оборудование из списка.
3. Исполнитель устанавливает флаг «Ремонт».

Ожидаемый результат: оборудование связано с документом, статус обращения стал «В ремонте», изменение видно в истории.

### S-04. Передача требования в разработку

1. Создать обращение с флагом «Требуется разработка».
2. Выбрать систему.
3. Открыть доску, относящуюся к системе и имеющую статус «Ведется разработка функционала».
4. Открыть созданную карточку разработки.
5. Назначить аналитика и разработчика, добавить подзадачу и часы.
6. Переместить карточку по статусам до «Выпущено в релиз».

Ожидаемый результат: на доске нет обращений других систем или без флага разработки; карточка разработки является дочерним документом обращения и имеет собственную историю.

### S-05. Поступление и выдача ТМЦ

1. Создать номенклатуру и складскую позицию.
2. Оформить отдельный документ поступления с организацией, складом, получателем и количеством.
3. Проверить увеличение остатка.
4. Создать документ движения оборудования со статусом «Новое» и сотрудником-получателем.
5. Провести документ.

Ожидаемый результат: остаток изменился, оборудование автоматически перешло в «Выдано», реквизиты документа и аудит заполнены.

### S-06. Работа оператора видеокамер

1. Оператор открывает расписание и журнал нарушений.
2. Создает нарушение с датой, объектом и описанием.
3. Прикрепляет фотографию.
4. Закрывает и повторно открывает нарушение.

Ожидаемый результат: фото открывается внутри карточки нарушения, доступ к вложению контролируется ролью, событие отражено в аудите.

### S-07. Инцидент информационной безопасности

1. Уполномоченный сотрудник принимает событие через форму или webhook.
2. Классифицирует запись, назначает ответственного и приоритет.
3. Добавляет комментарий и доказательство.
4. Переводит запись по статусам до закрытия.

Ожидаемый результат: запись доступна только разрешенным ролям, история неизменяема, вложение проверено по типу и размеру.

### S-08. Контроль руководителя и аудитора

1. Создать движение оборудования с флагом согласования.
2. Выбрать сотрудника-согласующего.
3. Выполнить согласование от имени руководителя.
4. Аудитор открывает журнал.

Ожидаемый результат: документ не может завершиться без согласования, решение и автор отображаются в истории.

### S-09. Отчеты, уведомления и профиль

1. Открыть Dashboard и перейти из метрики в отчет.
2. Открыть отчет и перейти из детализации в обращение.
3. Открыть уведомления, отметить одно и все уведомления прочитанными.
4. Открыть профиль и перейти в «Мои обращения» или «Проверку доступа».

Ожидаемый результат: переходы открывают соответствующие формы без потери контекста, непрочитанный счетчик корректно меняется.

### S-10. Отказ внешних компонентов

1. Остановить Redis, RabbitMQ или временно сделать внешний API недоступным.
2. Выполнить создание бизнес-документа и чтение данных.
3. Восстановить компоненты и проверить повторную доставку событий.

Ожидаемый результат: основной документ не теряется, ошибка диагностируется, outbox и идемпотентный consumer позволяют догрузить событие.

## 4. Критерии приемки

Сервис принимается при одновременном выполнении условий:

- все сценарии S-01—S-09 пройдены;
- S-10 пройден для целевого микросервисного контура либо зафиксирован как отдельная эксплуатационная проверка;
- нет дефектов P1 и блокирующих P2;
- права проверены на API и в интерфейсе;
- карточки обращения и разработки открываются отдельно;
- движения ТМЦ не создают отрицательных или дублированных остатков;
- вложения, аудит, уведомления и отчетные переходы работают;
- заказчик получил исходники, миграции, seed-данные, инструкции запуска и заполненный протокол ПМИ.
